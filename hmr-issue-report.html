1问题概述

在 ai-coding-project 项目初始化流程中，HMR（热模块替换）验证是关键验收环节。规范要求三步证据（baseline → changed → restored）的 documentId 必须完全一致，其中 performance.timeOrigin 是 documentId 的核心组成部分。

本次首轮 HMR 验证时，Begin 修改源码后 Vite 服务器触发了完整重启（而非模块级热替换），导致 timeOrigin 从 1792828555174.5 变为 1792828827039.6，三步 documentId 不一致，验证被拒。

3根本原因：Vite 依赖预构建未完成

Vite 在冷启动时会扫描并预构建（pre-bundle）依赖项（React、ReactDOM 等 node_modules）。这个过程在服务器返回 200 后仍在后台进行。

关键在于：HTTP 200 不代表服务器已稳定。

触发条件：服务器刚启动几秒内（依赖预构建尚未完成时）修改源码 → Vite 检测到源码变动但预构建未完成 → 触发服务器级重启（重新预构建）而非模块级 HMR → 浏览器完整重载 → timeOrigin 改变 → documentId 不一致 → 验证被拒。

4为什么第二轮成功

第一轮结束时，Vite 的依赖预构建已全部完成，服务器进入稳定状态。第二轮修改 App.tsx 时，Vite 只需做模块级热替换，不涉及重新预构建，timeOrigin 不变，HMR 正常生效。

验证结果被拒通过

5易触发场景

  • 容器环境，I/O 较慢，预构建窗口更长
  • 项目依赖较多（React + ReactDOM + 其他库）
  • 服务器刚启动几秒内就修改源码
  • 页面能加载（HTTP 200）但预构建尚未完成
注意：不是偶发 bug，是容器环境下时机敏感的已知特性。本地开发机性能好时预构建瞬间完成，不易触发；容器环境下概率显著上升。

6优化建议

  1. 等待服务器稳定后再开始 HMR 探针：服务器返回 200 后，额外等待几秒，确认 Vite 控制台不再有 optimizing deps 之类的输出，再记录 baseline。
  2. skill 规范补充等待步骤：在 reliable-initialization.md 第 13 行 baseline 步骤前，明确加一句"确认开发服务器已完全稳定（无 pending 预构建日志）后再记录 baseline"。
  3. 服务器就绪探测：可选——在脚本层增加一个"服务器稳定"探测（如轮询 Vite 的预构建完成日志或特定接口），自动化判断预构建是否完成。
  4. 失败后自动等待重试：首轮失败时，脚本可自动等待若干秒再重试一次，而非直接报告失败，减少人工干预成本。
当前规范定位：流程设计本身合理（已要求记录 timeOrigin 并校验一致性），主要空白在于未明确要求等待预构建完成。建议在规范层补充此步骤，可从根本上避免类似情况。
